# Radeon 780M H.264 解码性能与优化记录

## build 79 硬件解码性能 · 2026-11-24

三项优化（fence 等待、IDR 会话复用、回读刷新范围）已合入同一版内核，全部带运行时开关，默认全开。
测量条件：macOS 26.6.2、PhxBringup build 79、插件 v76p；机器上 Chrome 与编辑器界面本身占用约 30% 一个核，
绝对值比空载条件偏低 5–10%，同一次运行内的对照不受影响。

### 硬解满速吞吐（vt-metal，含 Metal 导入）

| 码流 | build 75 | build 79 | 变化 |
|---|---:|---:|---:|
| 1080p60（560 帧） | 193.2 fps | **275.7 fps** | +43% |
| 1080p（80 个 IDR） | 158.2 fps | **269.5 fps** | +70% |

### fence 等待

| 指标 | build 75 | build 79 |
|---|---:|---:|
| P 帧 ioctl p50 / p95 | 3.63 / 3.97 ms | **2.313 / 3.18 ms** |
| P 帧 IOSleep(1) 次数 | 1–2 | **0**（560/560 帧） |
| 阻塞时间 p50 | 2.19 ms | **0** |

剩余 2.3 ms 的构成：内核 on-CPU 约 1.1 ms（其中回读 memcpy 约 0.7 ms）＋ 硬件本身的 `fence_us` 约 1.2 ms。
等待侧已经没有可压缩的部分，1.8 ms 的旧目标不可达，验收判据按「ioctl − 硬件 ≤ 0.3 ms」理解更准确。

### IDR 会话复用

| 场景 | 关闭复用 | 打开复用 |
|---|---:|---:|
| 原生 1080p（80 个 IDR） | 174.2 fps | **269.5 fps** |
| stock FFmpeg 1080p | 90.2 fps | **110.7 fps** |

80 个 IDR 共节省约 1.28 s，即**每个关键帧约 16 ms**：原先每次关键帧都要关闭并重建固件会话，
现在只要分辨率、profile 和参考帧数不变且上一帧通过反馈校验，就直接复用。

### VideoToolbox 全链路（stock FFmpeg）

| 码流 | build 75 | build 79 |
|---|---:|---:|
| GOP 60（每 0.8 s 一个 IDR） | 93.2 fps | **110.7 fps**（+19%） |
| 原码流 | 90.2 fps | **110.7 fps**（+23%） |

提升幅度小于原生路径，因为 stock FFmpeg 建会话时要求 IOSurface 支持 OpenGL 纹理（约 3.3 ms/帧的额外转拷）。
同一台机器、同一条命令，去掉该请求的自编 FFmpeg 实测 **183.9 / 146.1 fps**（GOP60 / 原码流）。

### 实时播放 CPU（30 fps 定速，斗鱼 1080p）

| 配置 | 每帧 CPU | 单核占用 |
|---|---:|---:|
| fence 优化关闭（build 75 行为） | 7.04 ms | 21.1% |
| 自旋 + 预睡（默认） | **6.84 ms** | **20.5%** |

### 实际使用场景（直播 / 远程桌面）

单路 1080p30（斗鱼实时码流，定速 30 fps）：

| 模式 | 单核占用 | 每帧 | 解码延迟 |
|---|---:|---:|---:|
| 软件解码 | 28.0% | 9.68 ms | 8.4 ms |
| VCN 硬解 | **14.4%** | **5.10 ms** | **4.5 ms** |

多路并发（每路一条 1080p30 斗鱼流）：

| 路数 | 单核占用 | 每帧（合计） | 延迟平均值 | 帧数/错误 |
|---|---:|---:|---:|---:|
| 1 | 15.6% | 5.54 ms | 4.6 ms | 312 / 0 |
| 2 | 29.4% | 5.19 ms | 7.2 ms | 624 / 0 |
| 3 | 44.6% | 5.31 ms | 11.1 ms | 936 / 0 |

- 每路成本近似线性（约 15% 一个核），并发不降低效率；延迟随队列深度上升（4.6 → 11.1 ms），仍在 33 ms 一帧预算内。
- 1080p60 约为 1080p30 的两倍（约 30% 一个核）；满速约 275 fps，相当于 9 路 1080p30 的吞吐余量。
- `latency_max` 190–570 ms 的尖峰是起播或分辨率变化时重建会话的一次性开销，稳态不出现。
- 只有走 VideoToolbox 的 H.264 使用这条路径；远程桌面软件若用 HEVC/AV1 或自带解码器会退回软解，CPU 约翻倍。

### 正确性

五条码流共 1886 帧与软件解码逐帧一致：GOP60 560、原码流 560、斗鱼 540p 91、斗鱼 1080p 24、几何切换 651。
分辨率切换与损坏包都会重建会话（`dmesg` 里 `PhxBringup: AVC session rebuild`），稳态关键帧不再重建。

## build 75 软件解码与 VCN 硬解对照 · 2026-11-23

同一份 H.264 码流通过相同的 VideoToolbox API 分别强制软件解码和强制硬件解码。硬件运行报告
`using_hardware=true`，系统确认实际解码路径为 Phoenix VCN。CPU 时间统计本进程与
`VTDecoderXPCService` 的 user+sys 时间；内核解码工作计入后者。所有模式均为 0 帧错误。

测试使用 [vt-bench.c](../../tools/vcn/vt-bench.c)，每个码流分别在 30 fps 定速和不定速下运行。定速测试代表浏览器页签实时播放。

### 实时播放

| 码流 | 模式 | 单核 CPU | 每帧 CPU | 平均延迟 | 帧数/错误 |
|---|---:|---:|---:|---:|---:|
| 斗鱼 1920×1080 | 软件 | 31.8% | 10.60 ms | 9.85 ms | 240/0 |
| 斗鱼 1920×1080 | **VCN** | **18.8%（−41%）** | **6.25 ms** | **7.52 ms** | 240/0 |
| 斗鱼 960×540 | 软件 | 9.9% | 3.30 ms | 2.49 ms | 910/0 |
| 斗鱼 960×540 | **VCN** | **7.0%（−29%）** | **2.33 ms** | 2.81 ms | 910/0 |

1080p 样本每 0.8 s 有一个 IDR，比常见直播的 2–4 s 间隔更频繁。更贴近真实直播的关键帧密度应会进一步扩大 VCN 的 CPU 节省。
多开页签时，每路节省会累加；但所有 VCN 会话共享一个串行队列，总吞吐仍需按并发路数验收。

### 满速吞吐

| 码流 | 软件 | VCN |
|---|---:|---:|
| 1080p | 135 fps | 96 fps |
| 540p | 704 fps | 309 fps |

软件解码可以多线程并行；VCN 当前只有一个全局队列，所有流依次使用，且等待 fence 时使用 `IOSleep(1)`。
满速数字因此不代表播放体验：单路 1080p30 只占 VCN 约三分之一的理论吞吐，播放仍有充足余量。

### 关键帧延迟

| 模式 | 首个 IDR | 后续 IDR |
|---|---:|---:|
| 软件 | 20.9 ms | 约 9 ms |
| VCN | 340 ms（创建会话，仅一次） | **约 32 ms** |

后续 IDR 延迟来自每次关键帧都关闭并重建固件解码会话，以及通过 BAR0 未缓存路径清零整个会话区。
30 fps 下每帧预算为 33.3 ms，32 ms 的关键帧延迟可能造成每个关键帧附近丢一帧，表现为每隔数秒轻微卡顿。

## 会话生命周期检查

一次 90 s 浏览器采样没有播放任何视频，因此解码帧数为 0。页签开启时活动会话数为 1–2；关闭页签后
`PhxAvcActiveSessions` 回落到 0。本次观察未发现会话槽位泄漏。该结果只验证生命周期，
不代表持续播放后的吞吐或错误率。

## 优化计划（build 79 已实施前两项）

### 1. 关键帧复用解码会话（已实施）

当分辨率、像素格式和 SPS/PPS 参数未变化时，复用现有固件会话，只重置下一帧确实需要的上下文和反馈区域；
遇到分辨率或码流参数变化时仍退回完整的关闭/重建路径。目标是把后续 IDR 的约 32 ms 延迟降到个位数毫秒。

验收要求：

- 1080p 固定码流连续播放至少数分钟，所有 IDR 均成功，帧错误为 0。
- 后续 IDR 延迟稳定低于 10 ms，30 fps 播放不再因关键帧出现可见掉帧。
- 切换分辨率、SPS/PPS 或关闭流时仍能正确释放会话，活动会话数最终回到 0。

实施结果：稳态关键帧不再重建会话，每个关键帧约省 16 ms；原码流满速 158 → 269 fps；切换分辨率与损坏包仍能重建（`dmesg` 可见 `reason=`）。

### 2. 缩短 fence 等待（已实施）

当前轮询以 `IOSleep(1)` 为最小间隔，使每帧至少有约 1 ms 的固定等待，而且串行队列会放大总延迟。
可先采用有界的短轮询，在等待时间较长时让出 CPU；后续再考虑完成中断。不能用无界忙等换取吞吐。

验收要求：

- 满速 1080p 与 540p 吞吐提升，至少 3 路 1080p30 并发时无解码超时或错误。
- 短轮询期间额外 CPU 占用可接受，空闲或长等待路径不能持续占满核心。
- fence 超时、回绕和休眠/关闭路径继续通过现有诊断。

实施结果：自旋 → 亚毫秒睡眠 → IOSleep 兜底三阶段，P 帧 IOSleep 降为 0，ioctl p50 3.63 → 2.313 ms，30 fps 播放 CPU 6.84 ms/帧；自适应均值可经 `debug.phx_vcn_hw_ewma_ns` 读取或重置。

### 3. 降低首次开会话延迟（低优先级）

VCN 首次创建解码会话约需 340 ms，但只在起播时发生。可在会话创建阶段预热，或继续缩短固件/上下文初始化路径；
它不影响后续稳定播放，建议排在第 1、2 项之后。

## 复现

编译基准程序并运行同一码流：

    xcrun clang -std=c11 -O2 -Wall -Wextra -Werror vt-bench.c \
        -framework VideoToolbox -framework CoreMedia -framework CoreVideo \
        -framework CoreFoundation -o /tmp/vt-bench
    /tmp/vt-bench --software stream.h264 1 --realtime 30
    /tmp/vt-bench --hardware stream.h264 1 --realtime 30

在视频播放期间采样内核时序、活动会话和进程 CPU：

    python3 perf-capture.py 90 results/perf-build75

`perf-capture.py` 读取 `PhxAvcLastTiming`、`PhxAvcActiveSessions` 和 `phx-build`，并生成 `raw.json`、
`timing.csv` 与 `report.md`。测量时应关闭其他视频页签和后台解码任务，避免 `VTDecoderXPCService` 的 CPU 被其他流污染。

## 限制

- 数据来自单台 Phoenix/Radeon 780M 机器和 PhxBringup build 75，不能直接外推到其他 APU、驱动版本或分辨率。
- 实时测试码流的 IDR 间隔为 0.8 s，实际直播通常更长；当前数字可能低估播放场景的 CPU 节省。
- 软件解码多线程、VCN 单队列串行，因此满速吞吐与实时 CPU 节省给出的是两个不同维度的结论。
